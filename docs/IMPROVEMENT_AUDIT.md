## ما يعمل بالفعل

- مصادقة وجلسات آمنة ومؤسسات وRBAC وعزل على مستوى الاستعلام.
- PostgreSQL على Railway وترحيلات forward-only وفحص readiness للمخطط.
- مزودات OpenAI وAnthropic وGemini وOpenAI-compatible مع اكتشاف نموذج وفحص اتصال.
- وكلاء بإصدارات وتشغيل متدفق ومحادثات وسجل runs وaudit.
- Telegram Webhook موثّق ومنع `update_id` المكرر، وGitHub قراءة آمنة.
- تخزين مرفقات حتى 10MB وAPI v1 مبدئي لتطبيق أصلي.

## نقاط الضعف والمخاطر

- بعض Route Handlers ما زالت تجمع المصادقة والاستعلام ومنطق المجال؛ النقل يجب أن يكون تدريجيًا.
- تصميم الواجهة مربوط بألوان Tailwind داكنة مباشرة، مما يصعّب الوضع الفاتح.
- الدردشة تفتقد البحث والمسودات وidempotency صريحة وتتعامل مع Markdown كنص خام.
- أخطاء المزود والتكامل غير موحدة من حيث `retryable` والإجراء المقترح.
- لا توجد صفحة ملفات رغم وجود API، ولا Registry موحد للتكاملات والأدوات.
- التخزين داخل PostgreSQL مناسب للملفات الصغيرة لكنه يحتاج Object Storage عند الأحجام الكبيرة.
- Diagnostics لا تعرض بعد صحة المزودات والتكاملات ومعدلات التشغيل من بيانات فعلية.

## الاعتماد المتشابك

- `src/lib/agents/runtime.ts` يعتمد مباشرة على Drizzle والمزودات والأحداث؛ أي فصل يجب أن يحافظ على transaction وحدود المؤسسة.
- Telegram ينفذ خدمة الوكيل مباشرة بعد قبول webhook؛ `after()` مناسب للحمل الحالي، وQueue مطلوب عند التوسع الأفقي الكثيف.
- عقود لوحة الويب وAPI v1 ليست كلها مشتركة، مع وجود أساس جيد في `src/lib/http/contracts.ts`.

## وظائف غير مكتملة أو غير مرتبطة

- إدارة Platform API keys من الواجهة.
- تقييم الرسائل، تثبيت المحادثات، وحفظ المسودات في الخادم.
- مقارنة إصدارات الوكيل وCapability Map موسعة.
- اختبارات Telegram/GitHub الحية اختيارية ولم تُنفذ دون أسرار اختبار.

## قرارات الحماية

- لا تعديل لأي migration مطبقة؛ كل تغيير قاعدة بيانات في ملف جديد.
- لا كتابة GitHub أو حذف أو force-push.
- لا حزمة UI كبيرة؛ تُستخدم CSS variables والمكونات الحالية لتقليل الحجم والمخاطر.
- لا caching مشترك لبيانات المؤسسات.
- لا ادعاء ضمان انقطاع صفري؛ نعتمد idempotency، timeouts، readiness، circuit breaker وforward-fix.
